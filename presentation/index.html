2. Description

專案背景與需求分析 (Requirement Analysis)

⚠️ 傳統系統痛點與挑戰

  • 高頻輪詢負載瓶頸：雷達每 4 秒輪詢一次在空客機遙測，若每次皆深層運算將拖垮伺服器。
  • 冷數據重複查詢：機場代碼（20 個樞紐）、機隊與排班資料極少變動，重複讀取消耗資源。
  • PNR 暴力窮舉風險：傳統訂單僅憑 6 碼英數（如 BR1234）即可查詢，極易遭爬蟲枚舉撞庫。
  • 經度突變破線問題：越洋航線跨越 180° 太平洋換日線時，球面座標常產生穿球破線。

🎯 後端核心職責與設計目標

  • RESTful API 體系：嚴格依循 HTTP Method（GET/POST）與語義化狀態碼（200, 201, 400, 404）。
  • 自研 In-Memory TTL 快取：零外部 Redis 相依，以執行緒安全字典實現 TTL 自動過期與 X-Cache 標頭。
  • 雙因子防窮舉安全機制：強制比對 PNR + Passenger LastName，保護旅客隱私。
  • 球面航電數學運算引擎：Slerp 大圓航線插值與換日線平滑校正，精確模擬爬升、巡航與下降。

    created = create_booking(data)
    # 遵循 REST 規範回傳 201 Created
    return jsonify({
        "success": True, 
        "booking": created
    }), 201

def search_bookings(pnr, last_name):
    conn = get_db()
    cur = conn.cursor()
    # 雙因子安全驗證敘述：防止惡意窮舉 PNR 撞庫
    cur.execute("""
        SELECT * FROM bookings 
        WHERE UPPER(pnr) = ? 
          AND (UPPER(passenger_name) LIKE ? 
               OR UPPER(passenger_name) LIKE ?)
    """, (pnr.upper(), f"%/{last_name.upper()}", f"{last_name.upper()}/%"))
    row = cur.fetchone()
    return dict(row) if row else None
1. RFC 規範精確狀態碼 (201 Created) 不同於傳統一律回傳 200 OK，當成功寫入 SQLite 訂位紀錄時回傳 201 Created，表達資源已被持久化建立。
2. 雙因子防窮舉 (Anti-Enumeration) 傳統 6 碼英數 PNR 僅有約 21 億種組合，極易遭爬蟲以暴力枚舉刺探個資。本系統後端強制比對「訂位代號 + 旅客姓氏」，缺一不可。
3. 參數化防注入 (Parameterized Query) 使用 ? 預編譯參數進行 SQL 傳遞，徹底防範 SQL Injection 漏洞風險。

核心程式陳述：自研 In-Memory TTL 快取裝飾器

# backend/cache.py

def cached(ttl=300):
    """自研記憶體快取裝飾器 (支援自訂 TTL 與 HTTP 標頭)"""
    def decorator(f):
        @wraps(f)
        def wrapper(*args, **kwargs):
            if request.method != "GET":
                return f(*args, **kwargs)

            # 正規化排序 Query String 生成唯一 Cache Key
            query_items = sorted(request.args.items())
            query_str = "&".join(f"{k}={v}" for k, v in query_items)
            cache_key = f"{request.path}?{query_str}" if query_str else request.path

            # 快取命中 (Cache HIT)
            cached_data, age = cache.get(cache_key)
            if cached_data is not None:
                resp = make_response(jsonify(cached_data))
                resp.headers["X-Cache"] = "HIT"
                resp.headers["Age"] = str(age)
                resp.headers["Cache-Control"] = f"public, max-age={ttl}"
                return resp

            # 快取未命中 (Cache MISS) -> 執行原函式並回寫快取
            result = f(*args, **kwargs)
            cache.set(cache_key, result.get_json(), ttl)
            result.headers["X-Cache"] = "MISS"
            result.headers["Cache-Control"] = f"public, max-age={ttl}"
            return result
        return wrapper
    return decorator
1. AOP 裝飾器零侵入設計 以 Python @cached(ttl=3600) 裝飾器實現關注點分離，不用修改原有端點業務邏輯即可賦予毫秒級快取能力。
2. Deterministic Key 排序正規化 將 Query String 排序處理，確保 ?page=1&limit=5 與 ?limit=5&page=1 能精準識別為同一個快取 Key。
3. 標準 HTTP 快取標頭注入 主動回傳 X-Cache: HIT/MISS、Age 與 Cache-Control，前端與 Postman 測試人員可直接觀測快取狀態。

5. Discussion & Conclusion

技術討論與挑戰克服 (Discussion)

1. 高頻遙測輪詢 vs 快取的衝突與冷熱數據分流
討論：雷達每 4 秒輪詢一次，若快取會導致飛機定格；若不快取靜態資料庫又會超載。
對策：嚴格執行冷熱分流——對即時航電（/api/flights/live）堅決繞過快取（Bypass），對機場、機隊與時刻表則強制啟用 300s~3600s 快取。
2. 零外部相依環境下的快取實現
討論：教學展示環境缺乏 Redis 伺服器支援。
對策：採用 Python 記憶體字典加上 threading.Lock() 實作執行緒安全快取，並透過 X-Cache 標頭賦予與 Redis 一致的可觀測性。
3. 公開 API 之 PNR 暴力窮舉風險
討論：僅憑 6 碼訂位代號容易遭爬蟲寫迴圈遍歷撞庫。
對策：引進「雙因子安全比對（PNR + 乘機人姓氏）」，大幅提升窮舉難度至不可行級別。
